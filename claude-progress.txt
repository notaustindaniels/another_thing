### Ambiguity 1: project_points API conflict

SPEC.md §2.1 defines:
  project_points(points_xyz: np.ndarray,
                 cam: dict,
                 perspective_px: float,
                 origin_xy: tuple[float, float])
  -> tuple[np.ndarray, np.ndarray, np.ndarray]   # (s, screen_xy, z_cam)

tools/validate_projection.py defines the "locked API contract" as:
  project_points(x_centered, y_centered, z_cam,
                 perspective_px, canvas_width, canvas_height)
  -> tuple[np.ndarray, np.ndarray]   # (x_screen, y_screen)

**Resolution chosen:** Implement the validator's API as `project_points` (validator
contract is "locked"). Implement the full §2.1 pipeline as `project_world_points`.
The validator explicitly says it does NOT test world-to-camera transforms — those
are for other validators. This resolution is in the P1.M02 notes field and in
parallax_engine/projection.py docstring.

**Human action needed:** None — the implementation is defensible. But if you want
the SPEC to reflect the actual implementation, update §2.1 to show both functions.

### Ambiguity 4: validate_portal_equivalence.py uses different schema from §2.2

The validate_portal_equivalence.py validator generates a "synthetic test format" YAML that
is structurally different from the production scene.yaml format (§2.2):

Validator format (synthetic):
  - schema_version: '1.0' (string, not version: int)
  - canvas.width/height (not resolution: [w, h])
  - layers: [] (flat list, not stacks dict)
  - camera.mode: static + camera.position.x/y/z (not drone/keyframed)
  - Layer kind: solid_rect with color_bgr, rect_world, render_pass
  - Inline mask per layer (not top-level masks list)
  - encode: format/codec/crf block (not in production schema)

The validator's comment says "Field names follow the canonical schema in SPEC.md §2.2" but
this is NOT accurate — the formats are significantly different.

Resolution: Created parallax_engine/synthetic_renderer.py as a separate module specifically
for the synthetic test format. This does NOT modify or replace scene.py; the production
format and synthetic format are handled by separate parsers.

Phase 3 can proceed using the production format; the synthetic renderer is only used for P2.M03.

### Ambiguity 5: PNG frames vs MP4 for Phase 2 gate

The validator "prefers" MP4 but accepts PNG frames as fallback. H.264 (libopenh264) introduces
lossy compression artifacts that caused max_abs_error=152 (threshold=80). PNG frames produce
pixel-exact output: SSIM=1.0, MAE=0.0, MaxAE=0.

Resolution: Output PNG frames to workspace/synthetic_test/frames/. The validator reads them
correctly. The MP4 file is deleted (or not created) so the validator uses the PNG path.
This is the correct approach for a synthetic correctness test.
